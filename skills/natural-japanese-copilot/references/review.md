# 意味と読みやすさを確かめる

## 何を合格と考えるか

数値による自己採点は使わない。
重要なのは、意味に問題がないこと、読み手が理解できること、
保存した成果物が依頼に合うこと。

次の3つを分けて判断する。

| 確認 | 判断できること | それだけでは分からないこと |
| --- | --- | --- |
| 文字列の保護条件 | 指定表記の有無、回数、面ごとの対応 | 意味の一致、含意、誤った保護条件 |
| 日本語の見直し候補 | 一部の回りくどい表現や長い文の位置 | その表現が文脈に必要か、文章全体の自然さ |
| 原文・成果物との照合 | 追加・脱落・意味変更、文脈、表示上の問題 | 専門家だけが確認できる未検証の事実 |

補助ツールの終了コード0を、翻訳や自然さの合格証明にしない。

## 通常の確認

まず、原文と訳文、素材と成果物を比べる。
次に日本語だけを読む。
重要な数値、条件、結論はもう一度対応箇所へ戻って確認する。
直した箇所だけでなく、周囲との関係が変わっていないかも見る。

契約、制度、公開仕様、重要な対外資料では、
専門家や担当者の確認が必要な箇所を明示する。
確認していないのに「監修済み」「正確性を保証」と書かない。

## 補助ツールの入力

`scripts/review_japanese.py` はPython 3.10以降の標準ライブラリだけを使う。
ネットワーク接続や文書の書き換えは行わない。

- UTF-8の `.txt`：全体を `body` という面として読む。
- UTF-8の `.md`：見出し、箇条書き、表、リンクの表示文字列も対象。
- `.json`：`artifact-profiles.md` の `version` / `surfaces` 形式。
- Officeファイル、PDF、HTMLは直接読めない。対応するスキルで本文やラベルを取り出す。

Markdownのコードフェンス、インラインコード、URL、リンク先、
HTMLコメント、引用行は文体検査から外す。
元の文字列は保持し、保護条件ではそれらも検査する。
完全なMarkdown構文解析ではないため、複雑な入れ子は抽出済みの面データを使う。
除外した文字数や面は検査結果に表示する。

入力や設定を読めなければ終了コード2で止まる。
空の入力、未知の設定項目、重複した面IDもエラーになる。
検査できなかったものを「問題なし」として返さない。

## 保護条件を使う

先に原文から、残す表現・回数・面を決める。
翻訳を見てから条件を緩めると、検査にならない。
正当な訳し分けを追加するときは、原文と照らして理由を確認する。

```json
{
  "version": 1,
  "expected_surface_ids": ["body"],
  "checks": [
    {
      "id": "request-limit",
      "surface": "body",
      "source_excerpt": "at most five failed requests",
      "allowed": ["失敗したリクエストを最大5件"],
      "min_count": 1,
      "max_count": 1
    },
    {
      "id": "no-new-guarantee",
      "surface": "body",
      "source_excerpt": "The operation may fail.",
      "allowed": ["必ず成功"],
      "min_count": 0,
      "max_count": 0
    }
  ]
}
```

`expected_surface_ids` には抽出予定の面をすべて挙げる。
不足する面や予定外の面は、取り違えの可能性として報告される。
`checks` では、`allowed` のどれかに一致した回数を数える。
同じ位置で表現が重なる場合は、長い表現を優先し、二重には数えない。
正規表現ではなく、大小文字・全角半角を区別する文字列一致。
`max_count` は上限を置かないときだけ `null` にできる。

`surface` は面IDを指定する。`"*"` は全文の合計を確認する場合だけ使う。
値の入れ替わりを防ぎたいなら、全体ではなく各面に条件を付ける。
各面の中でも複数の対象があるなら、対象を含む十分に長い表現を指定する。
`"5"` だけなら `"15"` にも一致するため、裸の数値を意味の検査に使わない。

`source_excerpt` は人が原文へ戻るための手掛かり。
ツールはその引用が正しいか、許容表現と同じ意味かを判定しない。
原文にない新情報のすべてを、自動で見つけることもできない。

## 実行

```powershell
uv run --offline --no-project --python 3.14 python -B "<SKILL_DIR>/scripts/review_japanese.py" "<TEXT_FILE>" --contract "<CONTRACT_FILE>" --format json
```

入力ファイルは変更されず、結果だけが標準出力へ出る。
`--profile business` が既定。`technical`、`slides`、`ui` も選べる。
`slides` と `ui` では、本文向けの長文警告を使わない。

| 終了コード | 意味 |
| --- | --- |
| 0 | 文字列の保護条件に違反なし。未指定なら保護条件は未検査。文体の候補は残り得る。 |
| 1 | 指定表現の不足・過剰、対象面の不足・追加などを検出。 |
| 2 | 入力、設定、実行方法に問題があり、検査を完了できなかった。 |

JSON結果の `semantic_review` は常に `not_performed`。
`contract_status` が `not_run` のとき、意味や数値を検査したとは説明しない。
日本語がない入力では `style_status` が `not_applicable` になる。

## 指摘の扱い

文体の候補には、位置、該当表現、見直す理由が付く。
直すと読みやすくなるか、意味が変わらないかを確認する。
必要な表現なら残してよい。
重大な意味の問題が残っている間に、軽微な言い回しを延々と直さない。

スクリプトが使えなければ、上の観点で手動確認する。
実行していない検査について、件数や合格結果を作らない。
文体の修正は原則2回を上限の目安にし、判断が残るなら理由を示す。

## ルールの変更と回帰確認

`references/semantic-cases.json` は、翻訳・校正で守る意味の確認例。
良い例・悪い例は、人が意味を照合するための資料であり、
ファイルの形式が正しいだけで翻訳性能を測定したことにはならない。
ソースリポジトリから保守する場合は、リポジトリ直下のunit testsで
検査ツールの範囲と失敗時の挙動も確認する。

新しい言い換えルールを加えるときは、
改善する例だけでなく、変更してはいけない例も加える。
「できる」を消す、否定を反転する、値を別の対象へ移す、
条件を脚注だけに隠す、といった誤修正が見逃されないかを確認する。
